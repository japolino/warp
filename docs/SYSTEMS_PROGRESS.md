## Checkpoint 1: mechanical state and action receipts

Implemented in `src/living/mechanics.ts`, `mechanical-history.ts`, and the default runtime:

- Explicit source-backed resource values, counted items, equipment state and conditions. Unknown values do not become zero, and ordinary scenes do not acquire health, mana or survival meters.
- Pure, atomic preparation/commit for resource spending/recovery, item consumption, equipment changes and quantity-conserving transfers. Failed prerequisites reject the whole operation set. Receipt IDs, base-state hashes and recomputed changes guard against duplicates and stale/tampered receipts.
- The helper can interpret explicit known item uses, handovers, equipment changes and numeric spends from the player's action. It cannot invent healing, damage, rewards or ability costs through this path. Generic recovery is an internal primitive pending the ability/effect layer.
- A prepared receipt is saved before narration. The completed reply commits it independently of scene extraction. Cancellation spends nothing; retries and alternate swipes reuse the preparation and project only the selected branch. Deleting a swipe shifts its mechanical record with the narrative record.
- Bootstrap observations cannot refill spent stacks or reset balances to match fresh prose. Explicit OOC corrections can replace values. Edited causal paths invalidate the mechanical projection instead of reusing stale costs or inventing replacement balances.
- Conditions affect a classified approach, not every check. Effects can be scoped to a particular target and place. Blocking conditions send an unresolved/blocked receipt to the narrator and do not roll or spend. Native decision profiles classify method and, when people are present, target in the same evaluation call.
- Mechanical state is included in chronological prompt snapshots as resource/item/condition deltas. Receipts are turn-local. Public prompt packets omit historical evidence and transaction bookkeeping; full provenance stays in metadata. Prompt previews preserve already prepared receipts without model calls or mutation.
- Existing inline notes show the immediate resource/item change. No new drawer, setup wizard, genre selector or required sheet was introduced. The dice presentation is unchanged.

The runtime and engine fixtures cover a café wallet and bandages, oxygen recovery, location-limited terrain, person-limited suspicion, movement injury, interrupted spending, unavailable interpretation, failed extraction, swipe projection/deletion, edited history and cache stability. These are deterministic fixtures, not a live-model accuracy claim.

## Checkpoint 2: persistent ability content and optional inspection

`abilities.ts` now maps relevant established abilities into a bounded effect vocabulary. Sources are captured card/persona text and at most six activated lore entries fetched by ID in the owning user's scope. Hashed source snapshots travel with their definition records so later card edits cannot rewrite the mechanics used by past receipts. Preparation runs with the existing extraction call, or with the existing pre-action interpretation on first use; no rulebook or setup UI is created.

Definitions have stable owner/name IDs, versions, explicit costs, target policy, prerequisites, effects and source evidence. Repeated helper output cannot change a saved cost. Edited source mechanics or an explicit correction can create a subsequent version. A removed card/persona ability is not executable merely because its old definition remains in history. Invocation arguments cannot override a saved cost, and overlapping explicit charges cannot charge that cost twice.

The current effect subset supports restoring or damaging an established resource, applying a condition, and clearing a named condition. It validates targets, equipment and effect resources before spending, resolves costs/effects atomically, caps recovery, and skips success effects on an executed setback. Unsupported fields, formulas and restrictions are rejected or retained as explicit blockers, never silently dropped. Non-numerical effect amounts can use the small fixed 5/15/30 magnitude catalogue; these values are labelled Warp values and are not a claim of calibrated tactical balance. The broader encounter/effect system remains open.

The normal strip offers an optional Inspect button only when mechanical state exists. It opens a read-only inline view of player resources, counted items, conditions, and abilities. Individual abilities expand to costs, effects, prerequisites, source text and version. It does not expose card-derived NPC ability details, perform actions, advance time or invoke models. Newly prepared player abilities can show a short cost summary. The public extension state projects counted inventory instead of duplicating matching older prose facts.

## Checkpoint 3: shared identities, ordered defenses and action timing

The default mechanical path now uses shared person/object identities, aliases, sourced presence and pairwise touch/near/far distances. An identity learned after inventory or abilities already exist preserves the established owner name instead of duplicating that person. Aliases cannot merge two established owners. Profile sources can establish identity but cannot place a person in the current scene or assert a current death. Actual narrator evidence or an explicit correction owns those changes. Zero health means unable to act, not automatically dead; ordinary recovery cannot resurrect a person explicitly recorded as dead.

Resolver 2 prepares damage in a fixed order: immunity, flat equipped/condition armor, additive resistance capped at 100%, condition shields, explicit shield resources, then resource loss. Reflection uses actual loss and permits one return packet, which receives the recipient's defenses but cannot reflect again. Shield consumption is saved, and later repeated bootstrap prose cannot refill it. A wholly damage-based ability against established immunity is rejected before costs or a visible roll. Other effects can still be independently relevant.

Relevant definitions support sourced damage types, range, cooldowns, temporary conditions and defensive effects. Reapplying a definition's same effect refreshes it without stacking another copy. Unsupported types, formulas and restrictions still block instead of disappearing. Defend is an engine-provided stance with prototype 50% physical resistance until the actor next acts; it is not immunity to other harm or a calibrated balance claim.

The normal composer handles movement, guarding and waiting. A move changes one established distance band, and an ability checks range before paying. Cooldowns advance on that actor's supported executed actions, including an ability, movement, wait, guard, supply/equipment use once timing exists, and a normal resolved contested attempt. Definition costs do not count as a second action. Another person's action, an API wait, a question, inspection, a rejected action and a cancelled reply do not advance the player's clock. Temporary effects count subsequent actions of their affected owner. General fictional-time progression and unclassified mundane actions remain open.

The existing interpretation/extraction calls prepare these fields; there is no call per defense, actor clock or effect. The optional inspector shows saved shield capacity, damage type, range and cooldown. NPC identities or NPC-only mechanics do not introduce an empty player inspector. No encounter menu, genre selection or setup checklist was added. A singular explicit possession such as "You carry a medkit" can now establish one item without asking for an inventory count; an ability requiring a medkit does not itself prove ownership.

New receipts pin resolver 2 and include the resulting-state digest and deterministic event trace. Older receipts without a resolver marker retain the original arithmetic and acquire no new clocks or defensive reductions. Projection validates the saved result and events. A movement reply cannot contradict its own receipt, but a later actual movement event or explicit correction can update distance. Identity, distance, clock and cooldown changes append chronological prompt deltas; old prompt blocks remain unchanged.

The production sandbox fixture now also supports `bun scripts/mechanical-host-smoke.ts D:/Lumiverse --encounters`, covering a sourced ranged ability, payment, shield depletion and cooldown commitment in the actual host worker. This checkpoint still does not include autonomous NPC exchanges, periodic/buildup effects, resource links, companions, growth, a calibrated encounter resolver or sustained live-model playtests. The requirements below remain the completion target.

The production build, baseline worker check, inventory/ability/encounter worker checks and production frontend check against Lumiverse's actual DOM helper pass. New fixtures cover modern equipment first use, action timing, immunity despite a favorable model judgment, quiet scenes, aliases, depleted shields, bounded mutual reflection, exact saved projection, old resolver arithmetic and byte-stable historical prompts. ## Checkpoint 4: bounded NPC exchanges and visible response rolls

An exchange now stages the player's supported action followed by at most one response per present NPC, capped at three NPCs. The existing interpretation call selects sourced responses; no model call is made per participant or effect. Responses use stored ability versions, owned costs, equipment, range, conditions and the same defensive order as player actions. An ordinary unmodified physical strike is an engine-owned fallback at touch range for five physical damage against a known vital resource. This remains a prototype rule, not a calibrated replacement for an exceptional sourced attack or a complete model of arbitrary combat systems.

The model must quote a current opportunity from the latest narrator message. Code binds the actual message ID and revision locally. Quotes from an older threat or a profile cannot authorize a response. No response can choose a second player action, inject an outcome/roll, enqueue another response list or give one actor multiple responses. Offensive responses roll from the saved action/actor seed; ordinary sourced assistance can apply its benefit without an unnecessary attack roll.

Resolver 3 checks the resulting state after the player's action. Incapacitating an opponent prevents its response, cost and roll. A known range, cooldown or blocking-condition failure consumes that eligible NPC's opportunity without charging the unavailable ability. Its own clock advances, so a short block/cooldown cannot trap it indefinitely. Missing effect resources, unknown required distance, unsupported mechanics or an unresolvable reflection leave the whole exchange unresolved instead of letting one side deal free damage. Completed exchanges commit both sides once; cancellation commits neither side, swipes reuse the saved plan, and extraction failure cannot erase a completed exchange.

NPC rolls appear as smaller attributed dice rows below the reply. Each row independently uses the existing first-visibility animation, reduced-motion behavior and saved value. Ordinary repaints preserve every dice node. Visible names and actual action labels are shown; private assessment reasons and canonical hidden identities are excluded from those check summaries. Passive defenses apply without taking over the player's active reactions. A turn-local boundary tells the narrator to stop at the next player decision and leave arithmetic/resource recitation to the inline display. Prepared prompt snapshots now freeze the formatted receipt packet as well as the raw receipt, so future presentation-policy changes do not rewrite those saved prompt bytes.

Live-model testing exposed two avoidable bookkeeping failures: drafted narration in a message-ID field, and omitted resource IDs/name-based costs after an opening-read timeout. Local source binding, deterministic IDs and unique owned-name references now handle those shapes without a setup question. Ambiguous ownership or payment references still reject. A named correction preserves the original resource identity rather than creating a second balance.

## Checkpoint 5: physical consequences without numerical character sheets

Resolver 4 supports physical injury when a present person has no numerical vital resource. The engine records Lightly hurt/Hurt, Injured, Badly injured and Incapacitated conditions rather than inventing an initial Health value. A lesser injury affects supported physical approaches, not speech or every relationship. Incapacity is not death. Explicit numerical resources retain their arithmetic, and an exact source damage amount still requires a known resource. Mental effects, unmeasured objects, money and effort do not acquire a physical-injury fallback.

Source-backed qualitative harm and treatment share the existing defense, shield and bounded-reflection order. Optional sourced bodily resilience changes the engine's relative impact scale; rank, skill and emotional state are not bodily durability. The default ordinary scale is internal and requires no setup. These are prototype game interpretations, not calibrated source-system fidelity. The optional player inspector labels the interpretation and displays treatment restrictions without exposing NPC traits or a second hidden Health meter.

Treatment pays its established cost once and improves a recorded injury. A source restriction such as minor injuries only blocks more severe treatment before supplies are spent. Routine minor cuts can be treated, while lost limbs and special recovery conditions remain outside generic first aid. A living incapacitated player may explicitly wait for another present person's sourced aid without advancing their own action clock. Neither ordinary messages nor API waiting heal injuries.

New condition endings retain a causal retirement record, preventing an old injury quote or profile from recreating a healed condition. A later actual injury can be recorded. ## Checkpoint 6: causal knowledge for mysteries and social scenes

A disclosure needs an actual narrator quote identifying its participants and a sender who already knows that version. Player attempts do not prove completed hearing. No audience is inferred from the present cast, and arriving later cannot retroactively witness the earlier event.

Learning retains the exact proposition that person learned. A later correction or new fact does not silently update everyone's knowledge. A person can pass on an older proposition through their actual saved knowledge. Claims remain qualified in their source-backed text; learning an allegation does not imply agreement or make it true. Actual interpretation of a passage's meaning remains the helper's responsibility. Name/source/reference checks do not prove arbitrary semantic truth or that every hidden detail remains private in narration.

## Checkpoint 7: accepted multi-part agreements and conserved rewards

The default runtime now prepares an agreement from an actual acceptance and its sourced offer. Requirements retain distinct quoted clauses; all must be fulfilled. A player's attempt cannot complete one. A request alone cannot bind the player, and an NPC must actually accept a job offered by the player. Accepted terms are not regenerated on every read. Unsupported restrictions remain blockers. The helper still interprets which clauses and events mean what; the validator cannot independently prove that every possible natural-language restriction was captured.

Fulfillment and payment are separate. A completed job does not force the payer to cooperate. A sourced current offer makes a reward available, and a later refusal can withdraw it. An old offer quote cannot undo that refusal. A fresh genuine offer can create another agreement after the prior one settles, while repeating acceptance of the old offer cannot repeat its reward. There are at most three active structured agreements; the prompt/inspector retain those and the latest six settled agreements, with full paid history kept canonically.

Resolver 5 stages a normal-language collection or explicit player payment before narration. It transfers actual counted items or between two known compatible resource balances and marks that particular claim paid in the same receipt. It cannot mint a reward, assume an unknown wallet is zero, overfill a known cap, spend an equipped gift, turn health into currency, or automatically take the player's promised money. A known counted physical gift needs no numerical wallet. Each reward claim can settle once. Failed prerequisites and cancellation change neither side; selected swipes reuse the receipt; extraction failure cannot erase a completed payment. A saved setback during a genuinely opposed collection does not pay the claim.

Live testing exposed a missing connection between the sourced narrative cast and mechanical identities. The runtime now shares an already validated scene's participants when real mechanics need them. Ordinary quiet scenes still do not acquire a stat sheet. A later departure updates presence, while stale opening quotes cannot put that person back in the room. Missing bookkeeping is explicitly unresolved and does not authorize the narrator to invent an NPC refusal, extra fee or chore. This distinction addresses the observed bad consequence in the first live sample, but fresh live confirmation of the fix remains limited by timeouts.

The normal strip shows one brief progress line when a requirement changes. Immediate changes take priority over repeated reminders. Optional Inspect shows the actual clauses and whether a reward is promised, offered, withheld or received; opening it calls no model and collects nothing. There is no new drawer, setup wizard, named quest preset or required rulebook. The existing extraction call handles acceptance/progress; collection uses the existing pre-action path, with no call per clause or reward. Agreement/state boundaries append to future prompt snapshots and leave earlier narrator bytes unchanged.

## Checkpoint 10: persistent exploration through ordinary chat

Actual narrator discoveries and explicit OOC corrections can prepare places, containing places, current position, directional routes, access status, local discoveries and explicitly counted accessible supply stocks. Reading a map can reveal knowledge without moving. Hidden card maps and player attempts cannot create discoveries. Same-named rooms in different containing places retain separate IDs; ambiguous bare names cannot merge them. Location-scoped conditions bind to the appropriate place and cannot affect another same-named room.

Resolver 6 runs when exploration is relevant. `travel` validates the current place, direction and known access, then records arrival only on an executed success. `gather` requires a known local accessible stock and an explicit count; its decrease and the player's newly identified item stack commit atomically. Repeated bootstrap quotes cannot refill it. Another location, a locked cache, missing quantities, unknown route access and unmapped mandatory prerequisites block locally. Multi-operation plans roll back as a unit. Cancellation, source edits, swipes and reload use the existing receipt/path rules. Prior resolver 2–5 receipts retain their saved arithmetic and results.

A successful departure marks local people and loose objects absent and drops old actor distances. It retains carried equipment and does not grant an old-scene NPC a remote counterattack. Identity provenance is retained, so movement cannot turn a card-only name into publicly discovered identity. These are bounded departure semantics, not a full companion-following or travel-time simulation. Ordinary new space can still be explored in narration; it is not gated on a pre-authored map.

The optional Map presents actual known connections, not geographic distance. It distinguishes current/visited/known places, one-way routes, blocked or uncertain access, discoveries and depleted supplies. Browsing it does not invoke a model, send an action or advance an actor clock. First use requires no opening of the map, inspector or any setup panel. Spatial context for narration is bounded to 24 relevant places, 48 routes and 24 each of discoveries/stocks, while the full saved graph remains available to the map and later retrieval. Spatial changes append through persisted chronological deltas; earlier narrator prompt bytes remain unchanged.

Concurrency checks found two existing problems while integrating this. A background extraction that started before a reply completed could overwrite its newly committed receipt; mechanical saves now merge fresh receipts/observations under the shared metadata lock. Preparations now carry their original narrative path through completion, and refreshed state is validated before preparation. An edit to the player's action during narration therefore cannot execute its old transaction just because a balance is unchanged. Ordinary player metadata updates skip redundant extraction; actual older source edits and OOC corrections retain repair.
